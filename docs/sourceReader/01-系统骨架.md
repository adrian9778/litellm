## 0. 结论速览

LiteLLM 有两个生产和使用途径：**SDK 路由** 和 **代理网关**。它们最终都执行同一个核心操作——把一份标准化的聊天/嵌入/补全请求，通过路由逻辑分发给一个外部 LLM 供应商的 HTTP API，然后读回标准格式的结果。

| 结论 | 说明 |
|---|---|
| Native = 3 layers | SDK/Proxy → Router（RustCore） → Provider（HTTP CustomLLM subclass） |
| 100+ Provider | 所有供应商实现位于 `litellm/llms/<name>/`，统一继承 `CustomLLM`，请求在 `httpx` 层发出 |
| Gateway = FastAPI | Proxy 是 OpenAI 格式兼容服务器，代表性端点是 `POST /v1/chat/completions` |
| Router 有状态 | router 可以（也必须）持有编译好的 `model_list`；standalone（每请求重新解析）性能低 |
| Auth held by proxy | 代理网关承载 API Key 验证、租户、速率控制；SDK 侧只认 key |
| State需要持久化 | Redis（速率/Token/缓存/消息队列） + Postgres（prisma schema：key/team/model/spend） |
| 监控有专门服务 | Prometheus 指标、遥测、supervisor 的 optional |

## 1. 真实入口（谁、从哪里开始）

### 1.1 入口一：Python SDK（进程内调用）

**调用者**：任意进程内（服务函数、笔记本、调试工具）运行 Python 代码的开发者。

```python
import litellm

litellm.completion(model="gpt-4o", messages=[{"role":"user","content":"hi"}])
await litellm.acompletion(model="gpt-4o", messages=...)  # 异步
```

入口是 `litellm/main.py` 的顶层 `completion`（同步）/ `acompletion`（异步），以及 `litellm.Router.completion()`（带路由池化）。SDK 调用交给 `Router` 服务；没有 `Router` 时落到 `litellm.completion()`，由路径直接转发到供应商（`"the call is forwarded to the provider directly"`）。

### 1.2 入口二：OpenAI 格式兼容服务（代理网关）

**调用者**：任何支持 OpenAI SDK的客户端、SDK、curl / 屏幕客户端。

```
curl -X POST http://localhost:4000/v1/chat/completions \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer $LITELLM_MASTER_KEY" \
  -d '{"model": "gpt-4o", "messages": [{"role":"user","content":"hi"}]}'
```

入口是 `litellm/proxy/proxy_server.py`，`app = FastAPI(...)`；外部 HTTP 流量通过 `uvicorn`/`gunicorn` worker 进程进入。代表性端点：`/v1/chat/completions`（含 `/chat/completions`、`/openai/deployments/{model:path}/chat/completions`）、`/v1/embeddings`、`/v1/models`、管理端点 `/key/*`, `/team/*`、agentic 端点 `/agent/*`。启动命令在 `litellm/proxy/proxy_cli.py`（`@click.command()` + `litellm` CLI 入口）。

### 1.3 入口三：Supervisor（官方管理面板）

**调用者**：运维者通过 http://localhost:4000/dashboard 或 UI 菜单设置。

UI 在 `litellm/ui/`（Next.js 15 dashboard + Nginx），管理 API 中在 proxy 内（`/v1/...`）暴露。

### 1.4 部署面

`litellm/deploy/`：`docker-compose`（快速启动/测试）、`docker/`（官方镜像）、`terraform/`（云部署）、`helm/`（k8s）。官方推荐 `docker-compose.single_container` 或 K8s Helm。没有独立通知/告警服务；`cleanup`/监控由外部承担。

## 2. 生产主流程（数据/调用方向）

```mermaid
flowchart LR
  A[调用方: SDK / OpenAI 客户端 / curl] -->|1. 标准化请求| B(Litellm Proxy Server)
  B -->|2. auth / credit / rate| C[DB / Redis]
  B -->|3. Router 决策| D[Router (RustCore + 策略)]
  D -->|4. 选 Provider| E[Provider SDK: CustomLLM subclasses]
  E -->|5. HTTP 请求| F[LLM Provider API: OpenAI / Anthropic / Bedrock / etc]
  F -->|6. 标准化响应| E
  E -->|7. 结果与用量| D
  D -->|8. 响应| B
  B -->|9. JSON| A
```

**前提**：
1. `/etc/hosts` 或 `docker-compose` 解析；服务监听到 `host`；Postgres 与 Redis 先启动。
2. `model_list` 是合法的（见 3.），频带被限制。
3. `provider` 自己必须得到合理认证（API key）。

**单向数据流**（从请求到响应）：
- **输入**：标准化 `messages`（可选参数，包裹 `options`）、API key（如果有代理模式）、`model`。
- **处理**：auth → credit check → rate → router → provider → response。
- **输出**：云端/平台侧返回 `{"choices":[...], "usage": {...}}`。
- **接收方**：客户端，同 API 义。

**fallback**：任何一个 provider API 失败，router 按通道级策略降级重试。每通道尝试都可能失败，累计最多 `max_fallbacks` 次。**最终失败** → 向客户端返回 error（500 或供应商错误码）。

## 3. 服务角色与支柱（生产→开发对应）

| 服务 | 生产上的职责 | 开发实现 | 关键文件 | 可见失败表现 |
|---|---|---|---|---|
| Proxy Server | OpenAI 兼容入口/出口 | FastAPI app | `litellm/proxy/proxy_server.py` | 401/403/429/500; 服务不可用 |
| Router | 模型/供应商/负载均衡决策 | `litellm/router.py` + `RustCore` | `litellm/router_rust/core.py` | 路由.error；fallback |
| Provider | 执行通信到供应商 | CustomLLM 层 | `litellm/llms/custom_llm.py` + `*provider*/` | 供应商 API error |
| Redis | 速率//token balance //缓存 //MQ //E2E | `litellm/redis/` | `litellm/redis/stores/*` | 速率限制; Token 失效 |
| Postgres | 持久化审计/费用/模型/团队 | Prisma `litellm/proxy/db` | `litellm/proxy/persist` | DB 宕机; 开始慢 |
| UI | Dashboard | Next.js | `litellm/ui` | 401/500; 坏消息 |
| Prometheus | 指标 | `prometheus_metrics_server` | `litellm/proxy/prometheus_metrics_server.py` | metrics 层 |

所有服务其实是一个 **Redis/Postgres connection 共享架构**。一个进程（代理）能消耗它们。大型部署有 worker。

## 4. 外部依赖和可见失败

| 依赖 | 什么时候用 | 失败可见（代理） |
|---|---|---|
| 供应商 HTTP（OpenAI / Anthropic / Bedrock / Vertex / Azure / 等）| 所有聊天/嵌入调用 | 供应商返回 error → proxy error → 客户端 |
| Postgres | 代理开始, 官方声明和审计 | 如连接失败, 代理不会启动或启动部分 |
| Redis | 速率 / token / 缓存 | 如果连接失败, 速率/缓存会出现丢弃式fallback |
| Docker/OCI | 构建/部署 | 无法构建/拉取 |
| 终端支撑 (email, webhook) | 选择性告警/通知 | 如果不可用则跳过 |
