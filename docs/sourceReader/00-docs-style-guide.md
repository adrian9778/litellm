# 规范与定位约定

> 本文档（`00-docs-style-guide.md`）是 `docs/sourceReader/` 文档库的行为规范与定位约定。**规范属于文档资产，不是产品逻辑**，所有文档必须一致使用，不用重复描述。

## 1. 文档定位

`docs/sourceReader/` 产出「源码锚定的阅读库」，读者是**想理解当前工作区代码的人**。目标三个：

- **让人能读**：生产视角先写（用户/调用方看到什么），再写开发视角（代码在哪实现）。
- **让人能核**：每个关键结论都给源码锚点（`文件:符号+偏移`），不是行号；操作前可拦截，操作后可验证。
- **让人能改**：开发视角写清真实模块/类/函数/文件/调用关系与数据模型，动手术前知道 touchdown。

## 2. 成稿顺序（不可倒置）

每一步都必须按以下顺序，不是可选：

1. **代码基准与结论速览** — 哪份代码、是否干净、能做什么、适用范围、3～7 条关键结论。
2. **生产视角** — 真实入口、参与者、前置条件、输入、处理、输出、失败表现。**隔离于文件/函数名**。
3. **逐环节拆解** — 一次真实操作串起来（真实例子 + 分步列表）。
4. **开发视角** — 源码地图、调用表、实现图、字段/错误/分支。
5. **验证、缺口与后续** — 已回核项 / 待验证项 / 联动清单。

生产在开发之前，两层之间 引用编号或班号，不混写。

## 3. 术语和标注

- 正文用中文；**源码路径、包名、类名、函数名、API、配置键、字段名保留原文**。
- 结论四标记仅用下面四种，不造新词：
  - `[源码未确认]` — 仓库里找不到证据，也不能断定没有
  - `[源码未找到]` — 已全量查过，确实不存在
  - `[推断]` — 有证据支撑的解释，不是原文写的
  - `[待运行验证]` — 需要外部环境/运行期才能确认
- 禁止占位词：`TODO` / `TBD` / `FIXME` / 「待补充」/ 「同上」/ 「略」/ 省略号。
- 图和列表达标：实质性专题至少一张生产流程图 + 一张开发实现图 + 结论速览表 + 生产条件与结果表 + 开发源码映射表。

## 4. 代码基准

文档头部必须写清：

```
> 代码基准：<branch>@<完整SHA> + 工作区状态>；核实日期：<YYYY-MM-DD>；范围：<覆盖与不覆盖的内容>
```

衡据条件：
- 工作区干净 → `branch@完整SHA（工作区干净）`
- 有未提交改动 → `branch@完整SHA + 本篇涉及的未提交改动` 并列出文件

## 5. 锚点记法

- 函数内：`path/file.py 函数：Foo 偏移：+24`，`+0` = 函数签名行；连续片段 `Foo+0~+20`。
- 调用关系：`调用方 Foo+6 ↓ 被调用方 makeNode`。
-  nargs 可享，Web 不见本章。
- **正文用符号+偏移，文末索引可给 `文件:绝对行号` 方便跳转复核。**

## 6. 图表与表

- 生产图节点必须是**真实参与者/入口/业务动作/可见结果**，不以抽象方框面世。
- 开发图节点必须是**真实文件/模块/类/函数/存储**。
- 跨对象先后用 `sequenceDiagram`，条件分支用 `flowchart`，状态变化用 `stateDiagram-v2`，多表关系必须 `erDiagram`。
- 每张图下面必须有说明：前提、分支、终点。

## 7. 写入边界

- 本库只写 `docs/sourceReader/` 及 `.progress/`，不碰应用源码（用户明确要求除外）。
- 不修改仓库其他位置、宿主配置目录、hooks、settings。
- 只读不写（分析任务），DELETE/UPDATE 绝不做。

## 8. 来源与日期

实测数据必须标注来源与日期，无权限/not-the-case 就写「未实测，待补」并标记 `[待运行验证]`。
